OpenAI's Performance Factory ran 1,700 Codex investigations in 90 days, root-caused 600, graded 70 percent accurate.

OpenAI's engineering team published a Thursday essay from Members of Technical Staff Okay Zed and Cyrus Forbes documenting a production system in which Codex agents operate as always-on performance engineers inside OpenAI's network. Over three months the regression workflow tracked more than 1,700 autonomous investigations and root-caused more than 600 cases, averaging about 17 investigations per day. A manual review of a 100-case sample graded 70 percent of the Codex root-cause suggestions accurate. Three internal components do the work: a task service where engineers define workflows in Markdown and TOML, a dispatch loop that starts a Codex turn with the right instructions when a task is ready for its next step, and Cloud Codex, which runs each turn inside an isolated environment with scoped service-identity permissions and traceable actions. A shared skill called `perf-forensics` codifies investigation mechanics, including finding when a metric first degraded, separating slower requests from more slow requests, and running an adversarial Codex reviewer that tests counterfactuals. Brendan Gregg, Pieter Hooimeijer, Nick Cooper, and Louis Brandy are among the acknowledged contributors.

OpenAI Engineering · 2026-11-20 · Source ↗

The Thursday essay, "How OpenAI's Performance Factory Keeps ChatGPT Fast," is the most technically detailed public account OpenAI has yet published of Codex running as a staff engineer inside its own network. Zed and Forbes frame the exercise as a response to a specific scaling problem: the research org ships features faster than a human on-call rotation can read regression alerts, and the gap had grown wide enough that regression triage was starving. Before any agent was wired in, the team had already assembled more than thirty internal performance tools (profilers, tracing hooks, request-group comparisons). The agentic layer wraps those tools rather than replacing them.

Three parts: task service, dispatch loop, Cloud Codex

Workflows are declared in Markdown and TOML, with explicit state transitions, per-state agent prompts, and marker states that require a human. A dispatch loop polls for tasks whose next step is agent-driven and starts a Codex turn against that state's instructions. Each turn runs in Cloud Codex: an isolated environment inside OpenAI's network with scoped service-identity permissions. The agent writes progress back into the task and advances the state when the step completes. The design explicitly keeps engineers in the loop at merge: the bottleneck, Zed and Forbes note, is review time, not Codex throughput.

The perf-forensics skill, and an adversarial reviewer

A shared skill called `perf-forensics` codifies how to investigate regressions. Agents first determine when a metric first degraded, since alerts only fire after a threshold crosses. They separate "slower requests" from "more slow requests" by comparing affected and unaffected request groups. They check when a code change actually reached affected traffic, then test whether the change could plausibly explain the symptoms. A second Codex instance, run as an adversarial reviewer, tests counterfactuals: whether unexposed requests stayed healthy, whether the proposed root cause survives contradicting evidence. The essay gives a worked example: when ChatGPT conversations started failing, the first agent traced the cascade to image-download errors; the adversarial reviewer noticed that the file-locating service had already recovered while image requests kept failing, so the diagnosis was reopened and corrected.

"Agents can investigate more regressions than a team has time to read about. We want engineers to spend their attention on decisions rather than reconstructing the agent's work."— Okay Zed and Cyrus Forbes, OpenAI Engineering

What Codex is and isn't doing yet

A service-rightsizing skill flags autoscaling configurations keeping more replicas running than the load requires. A sample rightsizing report included in the post shows worker startup time more than doubling and names the specific pull request responsible. Zed and Forbes are candid about limits: proposed fixes can be overcomplicated or introduce new bugs, architectural tradeoffs still need an engineer, and every fix is reviewed and merged by a human. Proactive detection without alerts, synthetic performance tests for pre-review measurement, and cross-service rightsizing are listed as work in progress. Contributor thanks go to Brendan Gregg, Pieter Hooimeijer, Nick Cooper, and Louis Brandy — four names that read as a who's-who of systems performance.

"A test is only useful if we understand what evidence the investigator could see."— OpenAI Engineering essay

Gemini API previews Tool Retrieval: hundreds of tools without schema bloat.

Google · 2026-11-20 · Source ↗

Gemini API's Tool Retrieval preview lets agents keep hundreds of tool schemas on standby and load only the ones a task needs, preserving prefix caching and cutting prompt bloat.

Loher and Kassner, in a companion post with the Genie API team, previewed Tool Retrieval for the Interactions API. The pattern addresses a concrete scaling problem: as agents connect to dozens or hundreds of tools, sending the full parameter schema for every tool on every request wastes tokens and defeats prefix caching. Setting `defer_loading: true` on a tool holds its schema back; the model sees only the tool's name and description. When the model decides it needs the tool, it requests it by name, the API loads the schema server-side, and a function call is emitted in the same request.

Each step in the call surfaces in `interaction.steps`: `tool_search_call`, `tool_search_result`, `function_call`. Setting `defer_loading: true` on an `mcp_server` tool loads that server's tools on demand too, including remote MCP servers. Supported models are Gemini 3.6 and later, including all Gemini 4 models. There is no separate charge for Tool Retrieval itself; input and output tokens are billed at the model rate, and once a tool's schema has been loaded for a session, it is billed as input for the remainder of the conversation.

"Load tool parameter schemas on demand instead of sending your full tool library in every prompt."— Gemini API Tool Retrieval preview post

The practical effect is that Gemini agents can now be wired to a large catalog of tools, including whole MCP servers, without each turn paying the full catalog cost. It is a measured response to the "context-window-as-tool-shelf" pattern that teams have been straining against since the first MCP servers landed, and it comes the same day LangChain pushed LangSmith Tool Gateway into public beta with its own identity, deny-policy, and approval-gate layer for the same problem — two converging answers to one scaling constraint.

Compatible MCP clients at launch: LangChain, Deep Agents, Managed Deep Agents, Claude Code, and Cursor. Identity providers: Okta and Entra ID. The audit log is Enterprise-tier only.

"Route agent tool calls through a single URL with per-call credentials, deny policies, approval gates, and tracing across MCP servers."— LangChain product post

For enterprise teams running Claude Code and Codex side by side, the Gateway is the first first-party tool to put one audited surface in front of both, with approvals and deny policies that survive across agents.

DeepMind Institute publishes "From AGI to ASI" with a four-pathway framework.

DeepMind Institute · 2026-11-20 · Source ↗

Google DeepMind Institute mapped four paths from AGI to ASI — scaling, paradigm shifts, agent coordination, recursive self-improvement — and projected agent populations growing 1,000x by 2030.

Tim Genewein, a research scientist at Google DeepMind, summarized a new technical report, "From AGI to ASI," co-authored by Matija Franklin, Alexander Lerchner, Laurent Orseau, Samuel Albanie, Adam Bales, Cole Wyeth, Stephanie Chan, Iason Gabriel, Joel Z. Leibo, Allan Dafoe, Marcus Hutter, Thore Graepel, and Shane Legg. AGI is defined as "machines that match humans across nearly all cognitive tasks"; ASI as a system that consistently outperforms large expert groups with fewer resources, across nearly all tasks of human interest.

The essay maps four routes past AGI. Scaling: continue adding compute and data to current architectures. Paradigm shifts: move beyond next-token prediction into new architectures and training regimes. Agent coordination: compose many AGI instances into group agents or agent economies governed by multi-agent scaling laws. Recursive self-improvement: fastest in verification-rich domains like mathematics, software, and silicon design, where every output can be checked cheaply.

Numbers the report pulls together: compute per dollar grows 1.5x per year; algorithmic efficiency 3–6x per year; AI hardware spend 2.5x per year; combined effective compute 10x-plus per year. Inference efficiency alone drops compute demand roughly 4x per year. An Epoch study found consumer prices for a fixed benchmark score fell more than 13x per year since 2023. Projection: the effective population of AI agents could grow more than 1,000x by 2030 and a billion-fold within a decade.

"Because there are multiple routes to superintelligence, trying to slow down AI development by restricting just one area is unlikely to be enough."— Tim Genewein et al., DeepMind Institute

The paper's rhetorical function is to collapse the AGI-vs-ASI distinction into a continuous landscape, then argue that any single-chokepoint policy (scaling caps, compute export controls, algorithmic bans) leaves the other three pathways open. It lands the same day four US senators introduced an AI-disclosure bill, which is not accidental.
