Sol 6.1 is the intended engine wherever a task can tolerate a small quality delta in exchange for the pricing multiple; Codex, ChatGPT Work and the vast majority of Agents API traffic will route to it rather than to Astra.

"Nearly matches GPT-6 Astra's intelligence on agentic coding, computer use, and professional work at one-fifth of Astra's token prices." — OpenAI on GPT-6.1 Sol

OpenAI's move is not to cut the headline number but to attack agentic replay economics specifically through the cached rate. It is a bet that the DevDay Dots-plus-Agents-API bundle will move enough workload into the caching path that the effective price gap versus Anthropic on real agent loops becomes larger than the sticker-price gap suggests. OpenAI did not publish AutomationBench, GDPval, DeepSWE or Terminal-Bench numbers for Sol 6.1 in the keynote, so the "nearly matches Astra" claim is currently company marketing pending independent leaderboard scoring.

The math behind the top tier

OpenAI moves Agents API to public beta with hosted browser, MCP Events, and Codex Security Cloud.

Decrypt · 2026-09-29 · Source ↗

The Agents API entered public beta as a fully managed runtime handling sessions, orchestration and context compaction. It ships with an OpenAI-hosted browser, native MCP transport, and parallel subagents. MCP Events is a webhook-style extension contributed back to the MCP working group. Codex picked up cloud, voice control, native GitHub and GitLab code review, and a Security Cloud that scans entire repos and prepares fixes as pull requests.

For developers the substance of DevDay 2026 was the stack refresh around the Agents API, MCP and Codex. The Agents API moved to public beta as a fully managed agent runtime. OpenAI handles the session, the orchestration loop, context compaction as histories grow, and recovery when tools fail or an agent is interrupted; developers define the tools, the environments and the system prompts. The API now supports an OpenAI-hosted browser so any agent can be granted computer use without the developer running their own Playwright fleet or CDP proxy, connects natively to MCP servers as a first-class tool transport, supports parallel subagents so a lead agent can fan out to specialist workers, and keeps durable session state across long-running runs. The runtime brings what OpenAI describes as Codex's multi-agent capabilities, tool search, tool calling and context compaction into any application, productizing the machinery that powers Codex swarms internally.

Alongside the Agents API, OpenAI ratified MCP Events as an extension to the Model Context Protocol spec. MCP Events lets a plugin push webhook-style updates into an agent's session while the human user is offline; a monitoring plugin can flag a new alert, a code-review plugin can flag a merged PR, and the agent picks up the work on its next tick without polling. The extension is being contributed back to the MCP working group rather than kept as an OpenAI-only extension.

"The Agents API is a managed agent runtime: OpenAI handles sessions, orchestration, context compaction, and recovery while you define tools and environments." — OpenAI, DevDay 2026

Codex, from CLI to security scanner

Codex itself picked up four additions. Codex in the cloud is now included in most paid plans, letting long-running background coding tasks execute on OpenAI-hosted machines with a laptop closed and only pull artifacts down on demand. Code Review shipped with native GitHub and GitLab integrations across all plans, letting a user or agent request a Codex review on any diff without leaving the PR. Voice control landed end-to-end for driving the CLI hands-free and for reading review notes back to a user. Codex Security Cloud, available on Pro and above, scans entire GitHub repositories on demand or on a schedule, checks every new commit, investigates its own findings to remove false positives and duplicates, and prepares fixes as pull requests, all in the cloud. OpenAI also open-sourced the Codex harness itself — the software framework that runs Codex agent loops is now on GitHub, the first time OpenAI has released a full production agent runtime as source. The Agent Builder and Evals products from prior DevDays are being sunset on November 30, 2026, with the Agents SDK positioned as the durable path.

Decisions API turns Luna into a constrained-answer router; Private Intelligence previews confidential compute for fall.

DEV Community · 2026-09-29 · Source ↗

The Decisions API returns one answer from a developer-defined finite set, at Luna latency and Luna pricing, eliminating the free-text parsing step for routing and moderation. Private Intelligence is a hardware-attested confidential-compute runtime whose sealed enclaves the pitch says even OpenAI operators cannot read into. Decisions is in limited preview; Private Intelligence arrives fall 2026.

Two lower-profile DevDay announcements matter more than their stage time suggests. The first is the Decisions API, a new endpoint that focuses GPT-6 Luna's intelligence on a specific set of user-defined questions with finite pre-defined answers. A developer defines the question and the allowed answer set, and the endpoint returns one of the allowed answers at Luna latency and Luna pricing. It productizes the classification and routing primitive that developers have been hand-rolling on top of Luna and gpt-4o-mini since 2024, with the added guarantee that the return value is constrained to the enumerated answer set. That eliminates the free-text parsing step, removes the possibility of the model inventing an answer outside the allowed set, and makes the endpoint safe to wire directly into downstream code paths without a validation layer. Availability is limited preview at launch, with a broad release promised "in the coming days." The obvious downstream users are the Agents API and the Dot runtime — every agent needs a router in front of it to decide which tool to call or which specialist Dot to hand off to.

The second launch was Private Intelligence, an OpenAI hosting mode built around zero data retention and hardware-attested confidential computing. The promise is that a customer running an agent or a model call through Private Intelligence gets a sealed enclave whose contents cannot be read by OpenAI operators, only by the customer, and that no prompts, completions, tool calls or attachments are retained after the request. OpenAI's language is that even cloud operators cannot access the sealed data enclaves, a stronger claim than the standard zero-retention policy applied to Enterprise. It maps onto the confidential-computing hardware primitives Azure, AWS and GCP have shipped over the past two years. Private Intelligence is aimed at regulated buyers — health payers, defense contractors, financial-services desks and sovereign customers — who have been unable to route sensitive workloads through the standard OpenAI API for residency and access-audit reasons. It arrives in fall 2026 rather than at DevDay itself, and OpenAI did not commit to pricing or geographic availability on stage.

"Implements zero data retention with confidential computing infrastructure, preventing even cloud operators from accessing sealed data enclaves." — Decrypt on Private Intelligence

Building blocks, not products

Both announcements matter more as infrastructure than as headline products. The Decisions API is the routing primitive that makes multi-Dot workflows and Agents API subagent fan-out affordable at scale; without a cheap constrained-classification endpoint, every routing decision was either a small-model call with a parse step or a Sol/Astra call with output tokens billed. Private Intelligence is what makes it possible for regulated enterprises to sign the Agents API contract at all. The attested-runtime story will need third-party attestation reports and, ideally, an external audit before regulated buyers actually route production traffic through it; the confidential-computing story looks strong on the marketing page, but the substance depends entirely on which hardware provider OpenAI has attested against and whether the attestation is exposed to the customer, neither of which was disclosed.

Anthropic Frontier Red Team finds Zhipu's open-weight GLM-5.3 crosses Claude Mythos capability on autonomous exploits.

Anthropic Research · 2026-09-29 · Source ↗

GLM-5.3 scored 12 percent on Anthropic's ExploitBench and 4 percent on internal Binary Exploitation, versus zero on both for the prior generation GLM-5.2 and Claude Opus 4.6. Anthropic bypassed native safeguards 64 to 100 percent of the time via deceptive prompts and prefilled reasoning, and abliteration training took 2,200 GPU-hours at roughly $4,400 to drop refusals to between 3 and 12 percent.

Anthropic's Frontier Red Team published its assessment of Zhipu AI's open-weight GLM-5.3 on Tuesday, and the finding is unusually blunt for an Anthropic safety writeup: GLM-5.3 is the first non-Claude frontier model to demonstrate end-to-end autonomous cyber-exploit capabilities at the level Anthropic previously observed only in Claude Mythos Preview, its most gated internal frontier model. On ExploitBench, Anthropic's harness for measuring whether a model can autonomously write a working exploit for a known-vulnerable target binary, GLM-5.3 scored 12 percent against Mythos Preview's 14 percent. On Anthropic's internal Binary Exploitation benchmark, which measures full control-flow-hijack completion on hardened binaries, GLM-5.3 hit 4 percent and Claude Mythos Preview hit 6 percent. The comparison to prior generation is what makes this a threshold event: Claude Opus 4.6 and GLM-5.2 both scored 0 percent on both benchmarks, so the jump from "cannot" to "sometimes can" is discontinuous. In one representative case Anthropic's team used GLM-5.3 to discover previously unknown vulnerabilities in a browser JavaScript engine and chain them into a working exploit.

The safeguards story is the second half. GLM-5.3 shipped open-weight, and Anthropic tested three bypass techniques. Deceptive prompts engaged the model 64 percent of the time. Prefilled reasoning got 92 percent. Abliteration, the fine-tuning technique that identifies and removes the refusal direction in weight space, dropped refusal rates from over 90 percent to between 3 and 12 percent. Abliteration required roughly 2,200 GPU-hours at an on-demand cost of about $4,400. That is not a state-actor budget.

"A critical threshold in freely accessible capabilities has now been crossed. GLM-5.3 will likely give malicious actors access to capabilities that will allow them to find and exploit cyber vulnerabilities without meaningful restrictions." — Anthropic Frontier Red Team

Policy recommendation

Anthropic recommends that governments conduct independent safety testing on capable open-weight releases, that AI developers implement meaningful safeguards before open-weighting frontier capability, and that vetted defenders get expanded access to Claude at capability tier to counterbalance attacker access to GLM-5.3. Read alongside Sonnet 5.5's containment-boundary safeguards from Monday, the report positions Anthropic as the first US frontier lab to publicly benchmark a Chinese open-weight model as having crossed the Mythos capability threshold — a framing that will feed directly into next week's UN Security Council draft on frontier-model incident notification and into the Anthropic S-1 disclosures released the same morning.

The Beijing Academy of Artificial Intelligence (BAAI) team of Jingze Shi, Zhangyang Peng, Xianduo Li, Yanlin Qi, Xiaotian Lin, Haoxian Chen, Liangdong Wang, Guang Liu and Yuyu Luo released two paired attention-primitive papers featured together on Hugging Face's September 29 daily papers channel, drawing a combined 123 upvotes and marking one of the strongest showings for an infrastructure-attention pair this year. Both papers pursue the same objective — sparsifying attention while retaining full-attention accuracy — from two very different structural directions.

MassAlloc Attention (MALA) is the fused primitive. Its core insight is that in standard causal full attention, normalized softmax mass is spent on much of the score space where the contribution to the final representation is near zero; the wasted compute is enormous at long context. MALA implements a mass-allocation policy at the attention kernel level that preserves score-access to all valid causal interactions but skips compute on the low-contribution regions. Measured on a scaling ladder from 0.6B to 14B parameters, MALA delivers 2.2x training-latency reduction, 3.0x backward-pass reduction, and 1.6x inference-time reduction at 128K context, with maintained downstream accuracy on knowledge, reasoning and retrieval benchmarks. The training-FLOP reduction is proportional. Because MALA is a fused primitive, it slots directly into vLLM, SGLang and FlashInfer as a drop-in kernel.

"7.4x and 8.6x speedup in forward and backward training passes, and 3.0x faster decoding at 128K token contexts." — CoWA paper abstract

CoWA distributes history across heads

CoWindow Attention (CoWA) attacks the same problem from a structural direction: rather than every head attending to the full causal history, CoWA distributes access across KV heads. Every head shares a near-diagonal window (for local context) and a prefix-sink window (for the attention-sink phenomenon Meta documented in 2024), and each head is additionally assigned a distinct long-range window that covers a partition of distant tokens. Collectively, the heads still cover the full causal history, but no head is dense — the coverage is a collective property. Position-defined and requiring no learned components, CoWA is stable across training and inference. Measured on the same 0.6B–14B ladder, CoWA achieves 7.4x forward-pass and 8.6x backward-pass training speedup and 3.0x decoding at 128K, with accuracy parity to full attention. The paired papers together represent one of the more coherent 2026 attempts to reconcile the "one head does it all" dense-attention regime with the "assign a partition per head" sparse-attention regime that Google's Sparse Transformer and Anthropic's DSA had explored in parallel.

ByteDance's TraceDance paper, credited to sixteen authors led by Dehai Min and Daoan Zhang and including Philip S. Yu of the University of Illinois Chicago, appeared on Hugging Face's Sept 29 daily papers channel at 60 upvotes and represents a distinct kind of benchmark paper: one built entirely from real deployed-agent traces rather than synthetic scenarios. The system's automation pipeline, Anchor-and-Confirm, pairs programmable retrieval (a developer specifies the undesirable behavior in structured form) with LLM-based validation, and a companion Anchor Synthesis Loop iteratively refines the behavior specification until it matches enough real trace instances to constitute a benchmark. Testing uses decision-point continuation — the LLM under test is asked to complete an action from a recorded moment in a real trace, and its response is scored against behavior-specific criteria without reference to a specific right answer.

The pipeline chewed through 252,557 sessions and generated 107 benchmarks totaling 4,125 test instances, addressing 95.3 percent of developer-requested behaviors and reaching 84 percent human-review agreement on sampled cases. Nine leading LLMs — not named in the abstract, but community readers inferred GPT-6 Sol, Claude Opus 5.5, Gemini 4 Preview, Grok 4.8, Qwen3.9, DeepSeek V4.1, MiMo-V2.6-Pro, Mistral Large 3 and one open-weight model — achieved a mean success rate of only 26.7 percent across the 4,125 test cases. Three-quarters of the time, in other words, the frontier models fail at exactly the failure modes ByteDance's own agent operators have documented in production.

"Nine leading LLMs demonstrated a mean success rate of only 26.7 percent, indicating substantial challenges in appropriate agent responses at critical decision points." — TraceDance abstract

TraceDance is a methodology paper as much as a benchmark. Its practical use is that any organization running agents in production can point the pipeline at its own traces and get a benchmark suite specific to its own worst behaviors — a much closer proxy to real risk than the synthetic-agent benchmarks that have dominated the field. The HexaAnything paper from HexaFuture, credited to Hongcheng Gao, Jingjing Zhou and eleven co-authors, appeared on Hugging Face's September 29 daily papers channel at 91 upvotes and proposes a new bridge between the coding-agent world (which is where 2026's biggest capability jumps have happened) and the vision-language-action robot-control world (which has been the more slow-moving research frontier). The core proposal, which the authors call Physical Coding, is that task execution should be represented as code — Python, effectively — rather than as a direct language-to-action mapping. Current VLA models struggle to generalize because they implicitly encode task information into learned action sequences; representing tasks as code makes the intent explicit and lets the model use standard code-agent affordances (control flow, external tool calls, verification) at the same abstraction level as it would for a coding task.

The concrete system, HexaAnything, wraps VLA and WAM policies as tool calls the coding agent can invoke. It calls perception tools (object detection, pose estimation, spatial reasoning), planning tools (motion planning, task decomposition), and control tools (the VLA policies themselves), and makes in-the-loop decisions from external feedback such as sensor readings, task-progress signals or human corrections. On the RoboCasa365 benchmark suite — the 365-scenario tabletop and household-manipulation benchmark that has become the standard evaluation for household VLAs — HexaAnything reports improvements over VLA-only and code-only baselines, with the largest gains on tasks requiring multi-step verification and error recovery. The authors also demonstrate the system running physics experiments on tabletops autonomously, testing hypotheses about friction, elasticity or mass distribution with iterative experimental design encoded as code.

"Calls perception, planning, and control tools, including VLA/WAM policies, and makes in-the-loop decisions from external feedback." — HexaAnything abstract

Why architecture matters more than numbers

The paper's importance is less in the specific benchmark numbers and more in the architectural direction: 2026 has seen the coding-agent stack (Claude Code, Codex, Cursor, Devin) mature dramatically while VLA remains stubbornly narrow. HexaAnything is one of the first proposals to import the entire coding-agent workflow — plan-execute-verify-refine with external tool access — into the physical control loop, using code as the intermediate representation. A GitHub project by Low-Zi-Hong trended on Hacker News Tuesday at 148 points, distributing a 0.4-billion-parameter 1.58-bit BitNet-quantized language model across seven ESP32-S3 microcontrollers: one master handling BPE tokenization, embedding lookup and sampling, and six compute nodes each running four of 24 transformer blocks, connected via a DMA-driven dual-channel SPI daisy-chain.

A hobbyist GitHub project by Low-Zi-Hong titled ESP32s3-LLM-Cluster trended on Hacker News on Tuesday at 148 points and is a striking demonstration of how far the 1.58-bit BitNet quantization line has pushed edge-inference budgets. The project distributes a 0.4-billion-parameter transformer language model across seven Espressif ESP32-S3 microcontrollers, each of which is a $5 dual-core Xtensa LX7 chip with 8MB of PSRAM and no GPU. One node acts as master, handling BPE tokenization, embedding lookup (with INT4-compressed embeddings stored in about 14MB of on-chip flash), final RMS normalization, and output sampling. Six compute nodes each execute four consecutive transformer blocks (24 blocks total across the six workers), with each block computing RMSNorm, 1.58-bit ternary-quantized attention with RoPE positional encoding and KV caching, and a 1.58-bit MLP.

The interconnect is what makes the design interesting: rather than sharing a single bus, the seven nodes are wired in a dual-channel SPI daisy-chain, with DMA-driven transmit and receive so the CPU cores can compute while activations move between workers. Each compute node's PSRAM holds the KV cache for its assigned four layers, and the SPI transfer moves only the activation vector — small at 1.58-bit precision — between layers. The BitNet quantization is 1.58 bits per weight (ternary: -1, 0, +1), which fits the ~400M parameter model into roughly 80MB total across the seven-node cluster. The firmware is C++ against ESP-IDF with hand-written assembly for the 1.58-bit multiply-accumulate loop.

"Dual-channel SPI bus connecting master to node chain, DMA-driven transmit/receive." — ESP32s3-LLM-Cluster README

Sub-$50 hardware, existence proof

The repository (166 stars, 22 commits, MIT-licensed) includes a Python preprocessing pipeline that handles vocabulary pruning, weight quantization from the FP16 checkpoint, tokenizer serialization and binary packing for flash. There is no marketed throughput number in the README, but community comments on the HN thread reported figures in the 1-3 tokens-per-second range depending on prompt length. The project is significant less for the tokens-per-second number and more as a demonstration existence proof: distributed BitNet inference on sub-$50 hardware is now a hobbyist weekend project.
